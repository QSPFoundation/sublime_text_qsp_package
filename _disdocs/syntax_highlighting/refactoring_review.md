# Аудит подсветки: что можно упростить / реструктуризировать

Разбор `qsp_base.sublime-syntax` (1265 строк), `qsp.sublime-syntax` (62 строки), `qsp.qsrc.sublime-syntax` (38 строк).
Все рекомендации учитывают принятые ограничения: **поведение (scopes) должно оставаться 1:1**, контроль парности — `check_syntax_phase1.py`, тесты — `syntax_test_*.qsps`.

## P0 — самое крупное: n×2-дублирование plain/braced-контейнеров

Сегодня каждый контейнер существует в двух версиях:

| plain | braced-зеркало |
|---|---|
| `multiline_actions` | `multiline_actions_braced` |
| `multiline_act_pending` | `multiline_act_pending_braced` |
| `multiline_actions_body` | `multiline_actions_body_braced` |
| `multiline_loop` | `multiline_loop_braced` |
| `multiline_loop_pending_prewhile` | `…_braced` |
| `multiline_loop_pending` | `…_braced` |
| `multiline_loop_body` | `…_braced` |
| `multiline_conditions` | `…_braced` |
| `multiline_if_pending` | `…_braced` |
| `multiline_conditions_body` | `…_braced` |
| `multiline_actions_else` | `…_braced` |
| `multiline_actions_elseif` | `…_braced` |
| `multiline_elseif_pending` | `…_braced` |
| `multiline_elseif_body` | `…_braced` |

≈ **240 строк (шестая часть базы) — механические зеркала**, синхронность которых сейчас держится только на «СИНХРОН-КОНТРАКТЕ» (Фаза 5.1) и проверке `check_syntax_phase1.py` *после* того, как расхождение уже возникло.

### Вариант A — генерация braced-слоя на этапе сборки (рекомендуемый)

Sublime **не поддерживает параметризацию `include`** (нельзя сказать «вставь `location_body` ИЛИ `location_body_braced` в зависимости от окружения») — это фундаментальная причина дублей, обойти её декларативно нельзя. Но можно убрать *ручное* написание:

- оставить в файле только plain-контексты + явный маркер, например `# @braced: auto`;
- небольшой скрипт-препроцессор (рядом с `check_syntax_phase1.py`) разворачивает помеченные контексты в `_braced`-двойники по правилам: `location_body → location_body_braced`, `multiline_X → multiline_X_braced`, push-цели — аналогично;
- на выходе — тот же самый файл, что и сейчас (diff пустой при неизменности исходников), поэтому ничто в подсветке не ломается.

**Выигрыш:** один источник правды, sync-контракт выполняется *до* компиляции, а не постфактум; правки в одном месте.
**Цена:** ~50–80 строк скрипта сборки; нужно не забыть запускать его перед коммитом (можно встроить в существующий скрипт контроля).

### Вариант B — частичное сокращение без генератора

Вынести в braced-версии можно только *inline*-push-тела (см. P1.2): если тела else-arms станут именованными контекстами, их braced-двойники тоже станут однострочными include'ами. Полностью дублирование это не лечит, но уменьшает объём зеркал примерно вдвое.

## P1 — локальные упрощения внутри базы (поведение 1:1)

### P1.1. Дублирование regex-префиксов arms через переменные

Идентичные куски повторяются по 4–8 раз:

- `(?:^|(?<=\{))(\s*?)(?i:(act))` / `(?:^|(?<=\{))(\s*?)(?i:(\bif\b))` и т.д. — 6 контекстов × 2 arm'а используют один и тот же префикс `ARM_ANCHOR + ключевое слово`;
- lookahead-решения pending полностью идентичны в 4 парах (см. P1.4) и в braced-зеркалах.

Предлагаемые переменные:

```yaml
arm_anchor: '(?:^|(?<=\{))(\s*?)'
colon_block_eol: '(?=:\s*?(!.*?)?$)'   # act/elseif-версии отличаются знаком — см. P1.4
colon_single_eol: '(?=:\s*?\S)'
unbalanced_kw: '(?i:(\bloop\b)){{unbalanced_bracket_head}}'
```

**Выигрыш:** меньше визуального шума, единое место правки якоря. Риск нулевой при побайтовой идентичности раскрытого regex.

### P1.2. Inline-push-тела в `multiline_actions_else` (×5 arm'ов) и `multiline_actions_else_braced` (×5)

Тела push-стека расписаны inline и повторяют друг друга с точностью до `location_body` / `location_body_braced`:

```
- include: comment_after_colon
- include: illegal_multiline_else
- match: (?=^\s*{{elseif_else_final}}([^\&\n\r]*))
  pop: true
- include: wrongclose
- include: wrong_close_in_brace
- include: location_body[_braced]
```

Это **построчно идентичные сегменты** → их можно вынести в именованные контексты (в духе уже принятых `body_common_*` и `operacion_*_common`):
`else_body_common_head` (comment_after_colon + illegal_multiline_else + final-guard) и `else_body_guarded_tail` (wrongclose + wrong_close_in_brace + location_body / _braced).
Итого 10 копий × ~6 строк → 4 контекста. **Тот же приём применим к `multiline_actions_elseif` / `_elseif_braced`** (их первые два arm'а содержат идентичные тела).

### P1.3. Кандидат на удаление: 5-й arm `multiline_actions_else`

```
arm3: (?:^|(?<=\{))(\s*?)(?i:(\belse\b))\s*(:?)(?=\s*([^!\s].*)?$)
arm5: ^(\s*?)(\belse\b)(?=\s*$)
```

arm3 с опциональной `(:?)` покрывает почти всё пространство arm5: «else + пробелы + пустота/комментарий/конец строки». Единственное расхождение — `else   ` с **хвостовыми пробелами и без `!`**: arm3 захватит их в group3 и красит как `comment.qsp`, arm5 — просто pop без окраски. Разница косметическая, но **не нулевая** → убирать только осознанно (иначе arm5 можно оставить, перенумеровав nothing). Аналогично в `_braced`.

### P1.4. Pending-контексты: 8 шт. сводятся к шаблонам, отличающимся одной строкой

`multiline_act_pending`, `multiline_if_pending`, `multiline_loop_pending`, `multiline_elseif_pending` (и 4 braced-зеркала) построчно идентичны, кроме push-цели на `colon_block_eol` (плюс у `loop_pending_prewhile` — один дополнительный нулевой переход на `while`). Их тела можно собрать из общих include-сегментов (как в P1.2), тогда различие между семью из восьми контекстов — одна строка `push:`.

### P1.5. Хвосты «ошибочных» правил `no` — РЕШЕНО: сливать можно

Было:

```
operacion:         (?i:\bno\b)(?!\s*?{{right_operand}})   → invalid + scope avs_wrong_comma_with_out_left
operacion_subex:   (\bno\b)(?!\s*?{{right_operand}})      → invalid + тот же scope
```

**Решение (2026-10-28):** ключевое слово `no` регистронезависимо — как и все ключевые слова и имена пользовательских переменных QSP. Значит, различие «`(?i:)` vs регистрозависимая» в `operacion_subex` — недосмотр подсветки, а не зафиксированное поведение, и **пару правил `no` можно слить в общий сегмент** (по тому же принципу построчной идентичности, что `operacion_word_two_signs_common` / `operacion_ampersand_common`).

План правки:
- вывести общие правила `no` в сегмент (или в `operacion_word_two_signs_common`, либо отдельный `operacion_no_common`) с `(?i:\bno\b)`;
- ошибочный scope `avs_wrong_comma_with_out_left` (copy-paste от запятой; к тому же у правила с `(?!)` — это «без **правого**» операнда) заменить на **`avs_wrong_no_with_out_right`**;
- заодно сверить остальные вхождения `avs_wrong_comma_with_out_left` (строки 794/813/1015 базы) — они относятся к реальным запятым/амперсантам и остаются как есть;
- привязок к `avs_wrong_comma_with_out_left` вне базы не найдено (color scheme/TCE не ссылаются) — переименование безопасно;
- обновление `syntax_test_*.qsps`: ожидаемый scope для `NO`/`No` внутри `<< … >>` меняется с обычного на invalid — это **намеренная** поведенческая правка (fidelity к движку).

### P1.6. Общие сегменты, которые ещё не вынесены

После Решения-4/4B вынесены `operacion_word_two_signs_common` и `operacion_ampersand_common`. Остались построчно идентичные куски:

- **comma with_out_right + `(,)`** в `operacion` и `operacion_subex` — идентичны (различие только у with_out_left) → можно добавить `operacion_comma_right_common`;
- **правила `no`** — теперь тоже сливаются в общий сегмент (см. P1.5: `no` регистронезависима, различие по регистру было недосмотром);
- **`elseif_else_final`-guard** `(?=^\s*{{elseif_else_final}}([^\&\n\r]*))\n  pop: true` — 12+ копий одной строки; как переменная `final_guard: '(?=^\s*{{elseif_else_final}}([^\&\n\r]*))'` сокращает каждую arm-тело на шум;
- **список вызовов локаций** `(goto|gt|xgoto|xgt|gosub|gs)` в `location_call` (2 копии) и **`(jump)`** — стоит статьями переменных (`kw_calls`), заодно устранив рассинхрон с `kw_statements`, где они же перечислены внутри большого списка.

### P1.7. Пустые квантификаторы `s*?` (= `\s*`)

`\s*?` с lazy-«максимумом ноль» в пределах lookahead/backtrack-конструкций ведет себя идентично `\s*`, но читается тяжелее и мешает оптическому сравнению arms (например, `(?=\s*?.*?\:\s*?(!.*?)?$)` vs `(?=\s*?\:\s*?(!.*)?$)` — различие `.*?` vs отсутствует значимо, а `*?` у `\s` — нет). В safest порядке: нормализовать в рамках P1.1, **с обязательным прогоном тестов** — на чистом lookahead без последующих захватов влияние нулевое.

### P1.8. `strings`: одинаковый `meta_scope` для кавычек и апострофов

Обе ветки красятся `string.quoted.double.qsp` (сознательно, «поведение не меняем»). Для чистоты скоупов правильнее `string.quoted.single.qsp` для апострофов, но это **изменение результата подсветки** → только вместе с обновлением color scheme/тестов. Отмечено как «не трогать в рамках рефакторинга 1:1».

## P2 — `qsp.sublime-syntax`

### P2.1. `qspgame_header`: заменитель «первой строки»

```
match: (?<![\s\S])(?i:(qsp-game))(\s+.*)?$
```

Отрицательный lookbehind по любому символу — нестандартный способ сказать «только позиция 0 файла». Работает, но хрупко и неочевидно. Эквивалент по смыслу и почти поведению: `^` внутри `main` (правило включается первым и только в main, а `main` стартует с нуля строки). Однако из-за `set: diff` после первого правила заголовок больше не может сработать и так, поэтому можно упростить до:

```yaml
main:
  - match: ^(?i:qsp-game)(\s+.*)?$   # первая строка файла
    captures: ...
    set: diff
  - match: ''
    set: diff
```

**NB:** если `QSP-Game` встретится не на первой строке, текущий вариант его подсветит (lookbehind не сработает только в позиции 0), а упрощённый — нет. Проверить desired-поведение по grammar (`firstLine` в qsp_grammar.peg) — скорее всего, «нет» корректнее, но это **смена поведения**, вынести за рамки 1:1-рефакторинга.

## P4 — явные ошибки и подозрительные конструкции (не рефакторинг, а баг-лист)

1. **`qspdocs`, правило 1 содержит литеральное `...`:**
   ```
   (?:^\!@\s)([#$%](\d+|r) ... [#$%](\d+|r))(\s+\-\s+)(.*$)
   ```
   `...` здесь — три обычных точки, т.е. правило матчит только строки вида `!@ #1 XXX #2 - текст` (ровно 3 любых символа между). Похоже на незавершённый placeholder. Если имелось в виду «две ссылки на локации через любой разделитель», нужен `[\s\S]*?` или подобное. **Требуется решение, а не механическая правка** (изменит подсветку).
2. **Ссылка на память:** `!@`-строки в qsrc-файле (`# …`/`- …` как statements) — проверить, что `qspdocs` вообще применим к qsrc (в `main` включён) или это оверинклюд.
3. `preprocessor`: `^(\!@pp\:.*?)$` — lazy-`.*?` перед `$` избыточен, достаточно `(.*?)`→`(.*)`; поведение идентично.
4. **Разнородные scope'ы у однотипных начал:** `multiline_actions` вешает `meta.begin_action.qsp` на весь match заголовка, `multiline_loop` — `meta.begin_cycle.qsp`, а у `multiline_conditions` meta-scope на arm отсутствует вовсе. Это влияет на стили темы (act-строка помечается целиком, if — нет). Если различие историческое — унифицировать; если намеренное — задокументировать в `base_structure.md`.
5. `statements`: `(\b({{kw_text_statements}})\b)` — лишняя группа вложенности, `clr|clear` в `kw_text_statements` избыточно (`clr` матчится раньше `clear` той же альтернативы; ок, но можно `clr?` → **нет**, `clear` ≠ `clr+e`, оставить, просто noted).

## Что трогать НЕЛЬЗЯ (зафиксированные ограничения)

- **Слияние arms через внешнюю альтернацию якорей** — ложно расширяет набор позиций (отмечено в опыте п.2.1/3.1; арм `(?<=\{)` + `^` слиты корректно только потому, что оба якоря нулевой ширины).
- **Branch-reset `(?|…)`** — не поддерживается Onigmo этой сборки.
- **Порядок `wrongclose → wrong_close_in_brace → тело`** во всех guard-контекстах — единая дисциплина (п.3.3), менять можно только глобально и с тестами.
- **Любое изменение result-scopes** (P1.8, P2.1, P4.1, P4.4) — вне рамок 1:1-рефакторинга; требуется обновление `syntax_test_*.qsps` и прогон `check_syntax_phase1.py`.
