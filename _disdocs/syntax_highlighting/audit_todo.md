## P0 — видимые ошибки подсветки

- [x] **1. Внутри `<< … >>` скобки без пунктуации** — СДЕЛАНО 2026-10-30.
      БЫЛО: `subex` не инклюдил `brackets_inline` (он был только в `body_common_tail`
      и через него — в `location_body`), поэтому `<<$args[args['i']]>>` — `[`/`]` без
      scope, хотя рядом (`$arr[0]`) они красятся. Замер по корпусу `_examples`: **193**
      строки с `<<…>>`, где внутри есть `(`/`[`.
      СДЕЛАНО: `- include: brackets_inline` в `subex` ПОСЛЕДНИМ (после `users_variables`),
      с комментарием почему: anchor-правила `operacion_subex`, начинающие матч с `(`/`[`
      (`operacion_ampersand_common`, `(& x)`), обязаны пробоваться раньше.
      Ассерты (секция `# подвыражения << … >>`): `[`/`]` в `<<$a[0]>>` и
      `<<$args[args['i']]>>`, `(`/`)` в `<<($a + 1)>>`. Живой прогон 2026-10-30
      показал, что `&` в `<<(& $a)>>` НЕ помечается invalid (`\K`-правило
      не сработало в pushed-контексте — см. п.31), поэтому ассерт фиксирует
      ТЕКУЩЕЕ поведение (`keyword.operator.ampersand.qsp`) с пометкой
      «переписать на invalid, когда п.31 починят».

- [x] **2. Имена `@`/`@@` — только ASCII** — СДЕЛАНО 2026-10-30.
      БЫЛО: класс имени `[\w\.\#]+` (в Onigmo `\w` — ASCII), а грамматика говорит
      `userStatementName`/`userFunctionName = nonDelimiterChar+`, где `@` — сам `delimiterChar`,
      т.е. имя МОЖЕТ быть кириллицей. Не подсвечивались:
      `_examples/example_syntax_qsrc/sample_location.qsrc:46-47` — `@Функция(1)`, `@@Процедура(2)`
      (всего 4 случая в корпусе).
      СДЕЛАНО: выбрана вторая из предложенных форм — новая переменная
      `sugar_name: '[\p{L}\d_.\#]+'` (рядом с `users_variables`), подставлена во ВСЕ
      пять правил: `sugargosub` (1) + `sugarfunc` (4): `(\@\@)({{sugar_name}})`, три arms
      `(\@)({{sugar_name}})…` и invalid-arm `(\@{{sugar_name}}\s+{{right_operand}})`.
      ОТКЛОНЁН дословный `nonDelimiterChar` (`[^\s&'"(){}\[\]<>=!+\-/*\\,;:^@?]+`): тот же
      класс продублирован был бы четвёртый раз, а его отрицание нечитаемо; класс «буквы+цифры+`_#.`»
      — единый с `users_variables` (оба — про ИМЕНА) и не шире грамматики по существу.
      Проверено зондом (аналог `\p{L}` в python `re`): `@@Процедура` → `@@Процедура`,
      `@Функция(` → `@Функция`, `@Ёлка(` → `@Ёлка` (т.е. `Ё` тоже покрыт — родственно п.10),
      `@ 5` — не матчится. `$`/`%` в имя НЕ входят (как и было).
      Ассерты (секция `# sugar-func`): `@`/`@@`-пунктуация + имя как `variable.function.qsp`.

- [x] **4. Копипаст-баг в lookahead `brackets_multiline`** — СДЕЛАНО 2026-10-30.
      БЫЛО: третья альтернатива `{{quote}}[^{{ap}}\n]*{{quote}}` исключала **апостроф**
      вместо кавычки (в ОБОИХ правилах — `(` и `[`), поэтому `"…'…"` не считалась

      `$x = ("Bob's" +` ⏎ `"dog")`. Проверено на `re`: старая версия lookahead'а даёт
      `False`, новая — `True`.
      СДЕЛАНО: `[^{{ap}}\n]` → `[^{{quote}}\n]` в обоих правилах; в шапку
      `brackets_multiline` добавлена NB-запись про «свой разделитель» (чтобы копипаст
      не вернулся). Ассерт: секция `# скобки: lookahead многострочности` — вторая строка
      под `meta.group.parens.multiline.qsp`, `)` = `punctuation.section.parens.end.qsp`.

- [x] **30. Спецкомментарии `!@` не работали как обычные комментарии** — СДЕЛАНО
      2026-10-30 (номер сквозной: стоит в P0 по важности, а не по порядку).
      ТРЕБОВАНИЕ: `!@` — это ВАРИАНТ комментария, отличающийся только окраской
      (`avs_speccomments`), а не отдельная конструкция. Он обязан входить в тех же местах,
      ломаться/заканчиваться там же и иметь ту же внутреннюю структуру, что `!`-комментарий.

      БЫЛО: `special_comments` — ОДНО плоское правило без `meta_scope`, `pop`
      и подсостояний (`match: (?<=\!)@.*?(?={{nr}}|$)`). Следствия:
      1. **глотало `&`** в end-хвосте: `end !@ доки & x = 5` — хвост не заканчивался;
      2. **глотало `}`**: `end !@ доки }` внутри `{…}` блок НЕ закрывал;
