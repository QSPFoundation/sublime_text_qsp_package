## 1. Формат файла: `.sublime-syntax` (YAML, version 2)

Sublime понимает два поколения описаний синтаксиса:
- **старый** `.tmLanguage` (XML/PLIST, наследие TextMate);
- **новый** `.sublime-syntax` (YAML, `version: 2`) — именно он у нас. Он мощнее: контексты, переменные, `push`/`pop`/`set`, `embed`, кросс-файловые `include`.

Верх файла — это метаданные языка:
```yaml
name: QSP                 # имя в меню выбора синтаксиса
scope: source.qsp         # корневой scope (валидный, обязателен)
file_extensions: [qsps, ...]  # автоопределение по расширению
first_line_match: ...     # автоопределение по первой строке
version: 2
hidden: true              # (есть только в qsp_locations) — не показывать в меню
```
`hidden: true` у `qsp_locations.sublime-syntax` означает, что он не виден пользователю в списке синтаксисов — то есть это **вспомогательный** файл, рассчитанный на подключение из основного (через `extends`/`include`), а не на самостоятельное использование. Но сейчас этого подключения нет — об этом ниже.

## 2. Блок `variables` — текстовые подстановки

`{{kw_operators}}`, `{{right_operand}}` и т.п. — это **чисто лексическая подстановка** строк в регулярки перед компиляцией. Никакой логики, просто макросы, чтобы не дублировать куски. `(?ix:...)` — флаги regex: `i` (регистронезависимо), `x` (extended — позволяет переносы строк и пробелы/комментарии внутри паттерна). Это мы видим в `kw_operators`, `functions_num` и др.

## 3. Ядро — `contexts`: стековая машина построчного распознавания

Это самое главное. Sublime обрабатывает текст **не как единый поток, а как последовательность строк**, и для каждой строки поддерживает **стек контекстов**:

- Точка входа — контекст `main`.
- Двигаясь по строке слева направо, движок по очереди применяет правила контекста, лежащего **на вершине стека**.
- Правила проверяются **в порядке объявления** — **первое совпадение выигрывает**, остальные игнорируются. Поэтому порядок в `contexts` критичен (более специфичные/«ошибочные» правила стоят раньше общих).
- Каждое правило может:
  - `scope:` — назначить scope совпавшему тексту (или `captures:` — по группам);
  - `push:` — положить на стек новый контекст (можно анонимный — инлайн-блок прямо в правиле, как у нас в `multiline_actions`, `strings`, `figure_brace`);
  - `pop: true` — снять верхушку стека;
  - `set:` — заменить текущий контекст (у нас `main` → `set: diff`);
  - `include:` — протянуть правила другого контекста этого же файла **в текущей позиции**;
  - `meta_scope` / `meta_content_scope` — обернуть весь контекст/его содержимое в meta-scope (служебная разметка без прямого цвета);
  - `clear_scopes: true` — сбросить inherited scope (нужно для вложения HTML, у нас в `subexpression` и `htmlsupport`);
  - `with_prototype` — правило, применяемое ко всем вложенным контекстам (мы не используем, но полезно знать).

Именно поэтому в файлах так много костылей вида `^`, `(?<=\{)`, `(?=\s*?...\:...\!...)` — движок не «видит» строку целиком как AST, он матчит локально на вершине стека, и состояние (внутри мы `act`-блока, внутри `{}`, внутри строки и т.д.) кодируется **тем, какой контекст лежит на стеке**. Пример: `figure_brace` пушит контекст с `meta_content_scope: meta.block`, где рекурсивно `include: location_body`, и `pop` по `}`. Это и есть «скобочный» стековый механизм.

## 4. Scope → цвет (через color scheme)

Сам файл синтаксиса **не красит** — он навешивает иерархические scope-имена (`keyword.control.qsp`, `string.quoted.double.qsp`, `invalid.illegal.qsp`, `entity.name.location.qsp` …). А уже цветовая схема (`.sublime-color-scheme`) сопоставляет scope'ы стилям по принципу **наиболее длинного префикса**. Отсюда:
- стандартные имена (`comment`, `keyword`, `string`, `invalid.illegal`, `constant.numeric`, `entity.name.*`, `support.function`, `variable.language`, `punctuation.definition.*`) дают «бесплатные» цвета из любой темы;
- `meta.*` — служебные, обычно бесцветные, но цепляются правилами/плагином;
- **наши `avs_*` / `main_comment_start.qsp` / `brace_comment_start.qsp`** — это НЕ для цвета. Это маркеры-«заметки» на скоупе, по которым Python-плагин (`qSpy`) потом находит точки для диагностик/гомо-списков/переименований. Их нельзя терять при рефакторинге — они часть API подсветки.

## 5. Отношения между нашими двумя файлами (и главный «техдолг»)

Вот что важно понимать перед переделкой:

- **`qsp.sublime-syntax`** (`source.qsp`, видимый) — полный язык: распознаёт заголовок `qsp-game`, структуру локаций `# … --` (`location_def` + `meta.diff`-фолбэк), и всё тело.
- **`qsp_locations.sublime-syntax`** (`source.locations.qsp`, `hidden`) — по сути **клон** того же самого, но `main` сразу берёт одиночную локацию (`#`…`-` как locstart/locend) без заголовка/разбора всего файла. Предназначен для подсветки **одной локации** (вставка/предпросмотр).
- Сегодня они **почти полностью дублируют друг друга**: `variables`, `location_body`, `multiline_*`, `operacion`, `functions`, `system_variables`, `comments`, `strings`, `htmlsupport` — copy-paste на ~600 строк. Разница только в `main`/`diff`/`location_def`/`qspgame_header`.
- В файле прямо висит **TODO на строке 16**: вынести часть подсветки в `qsp_locations` и расширить через `extends` (или наоборот). То есть задумка была в том, чтобы один файл был базовым, а второй подключал общие контексты.

Кросс-файловое переиспользование в Sublime делается тремя путями:
1. `extends: qsp_locations.sublime-syntax` — наследование (нельзя наследовать «hidden в not-hidden», но base-файл-каркас работает);
2. `- include: qsp_locations.sublime-syntax#context_name` или по scope — pulling конкретного чужого контекста;
3. `- meta_include_prototype: false` + инлайн-вложение.

Это как раз то, что позволит устранить дублирование при рефакторинге.
