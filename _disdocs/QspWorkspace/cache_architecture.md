# Идентичность проекта и хранилище кэша `QspWorkspace`

Архитектурный документ. Фиксирует данные, выводы и решения по трём связанным вопросам:

1. **Что считать «проектом»** (идентичность, по которой живёт воркспейс и его кэш);
2. **Где и в какой форме хранить кэш** `qsp-project-workspace.json`;
3. **Как восстанавливать реестр `QSP_WORKSPACES`** в рамках сессии Sublime Text.

Правила ведения: решения не переписываются задним числом — каждое имеет `ID`, статус
(`принято` / `обсуждается` / `отклонено`), причину, отклонённые альтернативы и влияющие
пункты `refactor_plan.md`. Хронология — в разделе «Журнал».

---

## 1. Постановка проблемы

Сегодня:

- ключ реестра `QSP_WORKSPACES` = `window.folders()[0]`, который в коде называется `project_folder`
  ([structure.md#L62-L67](./structure.md));
- кэш — `qsp-project-workspace.json` **в этой же папке**, пишется единственный раз: при
  `on_pre_close_project` ([workspace.py `save_to_file`](../../QSP.sublime-package/qSpy/workspace.py));
- идентичность «проекта» нигде не выбиралась осознанно: модель сборки (`QspProject`) считает
  проектом ближайший предок с `qsp-project.json`
  ([project.py `_work_dir_init`](../../QSP.sublime-package/qSpy/project.py)), т.е. **другую** сущность.

Отсюда все симптомы, разбросанные по плану рефакторинга: фантомный WS при закрытии (2.1),
`IndexError` на пустом окне (2.2 и `project.py:81-83`), never-reset флаг закрытия (2.5),
три способа получить WS (4.1), протухшие пути в кэше, отсутствие инкрементальности (4.7).

### 1.1 Назначение WS — по вводным автора (05.11.2026)

`QspWorkspace` нужен для **живого индекса сущностей** проекта: названий локаций, меток, глобальных
переменных и прочего — из него питаются автодополнение, автоподсказки и тултипы. Отсюда иерархия:

1. **Первичен** виртуальный (RAM) индекс. Он пополняется вживую по мере редактирования и хранит не
   только имя, но и адрес сущности — в каком файле и в каком месте файла.
2. **Вторичен** файл кэша: чтение и запись — исключительно моменты **восстановления** и
   **закрытия** сессии. Файл не источник истины, он лишь экономит время пересканирования.

Инварианты, вытекающие из вводных (проверяются тестами):

- **И1** Файлы, не принадлежащие ни одной папке окна, в WS **не индексируются**: одиночный `.qsps`,
  открытый в окне проекта, остаётся просто открытым файлом. Сегодня инвариант **нарушен** в
  `on_post_save_async` — там нет проверки `is_path_in_project_folders`, в отличие от `on_load_async`
  и `refresh_from_views`.
- **И2** Виртуальный WS есть у **любого** окна хотя бы с одной папкой: сканируются все папки окна.
  Файл кэша при этом пишется **только** если окну сопоставлен `.sublime-project`; окно
  «Open Folder» живёт в RAM и при закрытии не оставляет файла.
- **И3** Индекс обновляется по факту изменения текста, а не только на load/save. Сейчас это
  компенсируется тем, что `on_query_completions` синхронно зовёт `refresh_from_views(...)` на каждый
  запрос ([`QSP.py:480`, `QSP.py:495`](../../QSP.sublime-package/QSP.py)): попап блокируется, а WS
  мутируется из UI-пути.
- **И4** Расхождение файла на диске с записями кэша (`mtime`/`size`/`md5`) → файл пересканируется.
  Несохранённый буфер всегда выигрывает у кэша и наружу не сериализуется.

## 2. Данные

`window.extract_variables().jsonc` — 9 снимков (5 самостоятельных + сценарные S1–S8), снятые
скриптом из комментария в шапке файла. Дополнительно: датчик событий
`QspProjectIdentityProbe` + `QspProbeIdentityCommand` + `plugin_loaded/plugin_unloaded`
в `QSP.py` (ВРЕМЕННО, выключатель `QSP_PROBE`), пишет в
`<sublime.cache_path()>/QSP/identity-probe.log`.

### Выжимка из снимков

| Снимок | `folders[0]` | `project_file` | `${folder}` | Вывод |
|---|---|---|---|---|
| 1 пустое окно | `[]` | null | null | ключа `folder` нет вообще → `.get('folder','')` == `''` |
| 2 одна папка = QSP-проект | папка игры | есть | == `folders[0]` | идеальный случай, всё совпадает |
| 3 `[lib]` (много библиотек) | `[lib]` | `easy.lib.sublime-project` | == `folders[0]` | в корне **нет** `qsp-project.json` → ST-проект ≠ QSP-проект |
| 4 игра + `[lib]` второй папкой | игра | игра | == `folders[0]` | один WS покрывает несколько папок |
| 5 игра-либы первой, JAD последней | `[lib]\easy.math.3` | `JAD.sublime-project` | == `folders[0]` | **`folders[0]` ≠ папка проекта** |
| S4 «Open Folder» (`games`) | `games` | **null** | == `folders[0]` | нет `.sublime-project` → нужен фолбэк идентичности |
| S5 активен файл вне проекта | игра | игра | == `folders[0]` | `${folder}` **не** проваливается на директорию файла |
| S7 активного файла нет | игра | игра | == `folders[0]` | то же |
| S8 два окна с одним проектом | — | — | — | **невозможно**: ST фокусирует существующее окно |

### Зафиксированные выводы

- **Д1. `${folder}` == `window.folders()[0]` во всех снимках**, включая пустое окно (оба `null`) и
  файлы вне папок. Гипотеза **H1** («при пустых папках `${folder}` = директория активного файла,
  поэтому `on_pre_close_project` пишет кэш в чужую папку») — **опровергнута**. Формулировка плана
  2.1 «пусто, если папок нет» — верна, фантомный WS под ключом `''` подтверждён.
- **Д2. `folders[0]` не является папкой проекта**: снимок 5 (наш собственный JAD) — ST-проект `JAD`,
  а `folders[0]` = `[lib]\easy.math.3`. Значит весь WS и его файл-кэш сегодня привязаны к
  **посторонней библиотеке**. Прежний «странный» снимок (`folder` = `Downloads\Telegram Desktop`
  при `project` = JAD) — тот же класс, а не аномалия API.
- **Д3. `project_file_name()` / `workspace_file_name()`** заполнены ровно тогда, когда есть
  `.sublime-project`, и `null` в «Open Folder» и в пустом окне → пригодны и как идентификатор,
  и как различитель типа окна.
- **Д4.** Коллизия «два окна одного проекта» исключена (S8). Коллизия двух разных проектов на одной и той же `folders[0]` теоретически возможна, но исчезает при идентичности по файлу проекта.
- **Д5.** Пути содержат не-ASCII, пробелы и квадратные скобки (`книги-игры`, `Denny VS Badboys`,
  `[lib]`, `[source]`) → нормализация ключа обязательна (`os.path.normcase` + `abspath`), любой
  разбор путей по `:`/пробелам запрещён (ср. с 1.5).
- **Д6.** В текущем `qsp-project-workspace.json` лежат **мёртвые пути** (`…\JAD\[examples]\…`,
  тогда как папка переименована в `_examples`): схема не версионирована, прунинга нет, кэш
  пережил переезд целиком и продолжает «оживлять» несуществующие файлы.
- **Д7.** Золотой факт для R2: **ST-проект ≠ QSP-проект**. Один ST-проект может покрывать несколько
  `qsp-project.json` (снимок 3), и один QSP-модуль может лежать вне `folders[0]` (снимок 4/5).
  Уровень кэша — окно/ST-проект, а не модуль.

## 3. Решения

### R1. Идентичность: два ключа вместо одного — `принято`

Из И2 следует, что «привязка WS» и «привязка файла кэша» — разные сущности, одним ключом их не
описать:

| Уровень | Ключ | Область |
|---|---|---|
| Виртуальный WS (RAM) | `window.id()` | любое окно с ≥1 папкой; чистка по `Window.is_valid()` |
| Файл кэша (диск) | `identity = normcase(abspath(window.project_file_name()))` | только окна с `.sublime-project`; `identity` пуст → файла нет |

- **Почему так:** RAM-ключ обязан переживать перестановку и добавление папок и не требовать пути
  вообще; дисковый ключ обязан быть стабилен (Д2: `folders[0]` может быть чужой библиотекой) и
  различать два `.sublime-project` в одной папке (потому `project_file_name()`, а не `project_path`).
- Связка устанавливается при загрузке: `on_load_project_async` → `WS.for_window(window)`, внутри
  хранится его `identity`. `save`/`load` ходят по **собственному** `identity` WS, а не по
  аргументу-пути — это само убирает класс багов «сохранили не туда» (2.1) и лишает смысла параметр
  `project_folder` у `save_to_file`.
- **Отклонено:** `folders[0]` как ключ реестра (Д2); `${folder}` (Д1 — это тот же `folders[0]`);
  hash от списка папок как **дисковый** ключ (И2: окну без проекта файл не нужен, а при добавлении
  папки ключ уехал бы); активный файл (не проектная правда).
- **Побочное следствие:** `window.id()` стабилен между событиями, но не между запусками ST —
  поэтому он и не может быть ключом персистентности.

### R2. Область действия — `принято`

WS окна = все `.qsps` (и прочие индексируемые файлы) **во всех папках этого окна** (И2), и ничего
вне этих папок (И1). В кэш пишется `scope: [folders]` вместе с `identity`: при загрузке это
отличает «добавили папку» (сканировать только её) от «другой проект» (другой кэш). Уровень
`qsp-project.json`/модулей — не уровень WS (Д7): один ST-проект покрывает несколько QSP-проектов.

### R3. Где хранить — `направлено` (cache_path, детали открыты)

Файл кэша — только для окон с `.sublime-project` (И2), и лежит он вне репозитория пользователя:
`<sublime.cache_path()>/QSP/workspaces/<project_base_name>-<sha1(identity)[:8]>.json` плюс
человекочитаемый `index.json` (`identity → файл, scope, дата записи`). Окна «Open Folder»
индексируются в RAM и на диск ничего не пишут.

- **За:** репозиторий игрока не пачгается (`.gitignore` для `qsp-project-workspace.json` больше не
  нужен); один каталог для «посмотреть/удалить/сравнить»; не зависит от порядка папок; не пишет
  файл в чужую библиотеку (Д2 — сегодня это происходит буквально).
- **Против и как снимаем:** кэш не виден «рядом с проектом» → команда `qsp_show_workspace_cache`
  (открыть файл кэша активного окна) и `qsp_reset_workspace_cache`.
- **Отклонённые альтернативы:** sidecar в корне проекта (Д2 + конфликт с VCS + уезжает при
  перестановке папок); `.sublime-workspace` через `Window.settings()` (семантически точно «юзер-
  сессия», но формат и момент флаша вне нашего контроля, объём на тысячи локаций); «не хранить
  вовсе» — план B, становится дешёвым при R4 с mtime-индексом (см. 4.7).

### R4. Что хранить: индекс сущностей, а не только локации — `обсуждается`

По И3 и вводной 3 в WS живут разные сущности, поэтому схема `v2` — не `locations`, а `symbols` по видам:

```json
{ "version": 2,
  "identity": "<abs path .sublime-project>",
  "scope": ["<abs folder>", …],
  "files":   { "<abs file>": {"mtime": 0, "size": 0, "md5": "…"} },
  "symbols": {
    "loc":   { "<abs file>": [["<name>", [start, end]], …] },
    "label": { "<abs file>": [["<name>", [start, end]], …] }
  },
  "global_vars": ["<name>", …] }
```

- `symbols` — данные выводимые, но храним: иначе на старте полное пересканирование (4.7);
  `files.mtime/size` — то, что делает 4.7 инкрементальным (И4).
- `global_vars` — **имена** (множество), они питают автодополнение; **регионы** переменных в кэш не
  пишутся и в проектный индекс не попадают: они относятся к конкретному вью (пункт 2.4 плана).
- Сериализуется только файловое место. Безымянные буферы (`Buffer.id()`) — RAM-only, как сегодня
  (`get_json_struct` их пропускает).
- Загрузка: пути, отсутствующие на диске, — отбросить (лечит Д6); `version` не совпал → rebuild;
  битый json → пустой WS + ошибка в лог (1.3) и обязательное пересканирование (И4).
- Пустой индекс пишем **явно** (решение пользователя), но только если WS был реально построен для
  этого `identity` (признак `built`); иначе пустой WS затрёт рабочий кэш после неудачной загрузки.

### R5. Жизненный цикл: живой индекс, файл — только закрытие/восстановление — `измеряется датчиком`

Пополнение индекса (RAM, primary — И3):

- `on_load_async`, `on_post_save_async`, `on_pre_close` — как сегодня, но всё через один accessor
  **без создания** и всё с проверкой И1;
- **новое:** `on_modified_async` с дебаунсом на вью → перескан только этого вью
  (`view.symbol_regions()`, как в `refresh_qsplocs`): это и есть «пишется вживую»; дорого на весь
  проект, дёшево на одно вью;
- `on_query_completions` **не** зовёт `refresh_from_views` (снять `QSP.py:480`, `QSP.py:495`) —
  попап читает готовый индекс.

Файл кэша (диск, secondary — вводная 3):

- чтение ленивое, по окну: `on_init` / `on_load_project_async` → `WS.for_window(window)` →
  `load_from_cache(identity)` → инкрементальное сканирование по `files` (снимает «зависания на
  старте», 4.7);
- запись: `on_pre_close_project` **+** `on_close_window` **+** `plugin_unloaded()` — и делает её сам
  WS по своему `identity` (без параметра-пути). Авто-сейв по таймеру **не** вводим: по вводной это
  вторичный момент. Какие из трёх точек реально приходят и в каком порядке — **Э1–Э5**;
- `pop` из реестра при закрытии + accessor без создания (иначе `on_pre_close(view)` вернёт фантом
  сразу после сохранения). После этого маркер 2.5, скорее всего, не нужен → удалить, а не переделывать;
- если `identity` пуст (окно без `.sublime-project`) — запись вообще не происходит (И2), но RAM-WS
  живёт до закрытия окна;
- восстанавливать список проектов не нужно: ST держит окна и папки в `Session.sublime_session`,
  `on_init` уже видит правильный набор; `project_history()`/`folder_history()` (4144) — только для
  чистки сироток (R6).

### R6. Миграция и сиротки — `отклонено без решения`

- Однократный импорт: если в `folders[0]` лежит старый `qsp-project-workspace.json`, а кэша в
  `cache_path` нет → конвертировать в `version: 2`, sidecar пометить/удалить.
- Сиротки: кэш-файлы, чей `identity` больше не существует на диске → удаление по возрасту
  (например, 90 дней без обращения).

### R7. WS как индекс сущностей (вводная 3) — `направление принято, объём не определён`

Что должно оказаться в индексе и как это выглядит сегодня:

| Сущность | Сегодня | По решению |
|---|---|---|
| локации | в WS (`refresh_qsplocs` по `symbol_regions`), обновляются на load/save; при подсказке — принудительный перескан всех вью | в WS, обновляются по изменению вью (дебаунс); completion читает готовый индекс |
| метки (`label_to_jump`) | **не в WS**: `QspWorkspace.get_qsplbls(view)` сканирует только текущий вью (`QSP.py:449`, `QSP.py:512`) → метки из других файлов недоступны | в WS как вид `label`; дополнение — по всему проекту |
| глобальные переменные | `_global_vars_names` только пишется, читателя нет (пункт 3.2 плана «удалить»); регионы пересчитываются per-view | **имена** — в WS (пункт 3.2 отменяется как «мёртвый код», потребность описана в todo.md:53); **регионы** — per-view, вне WS (2.4) |
| прочие (`obj`, вызовы локаций, имена сохранений, картинки из `scans`) | не индексируются | решать по мере появления потребителей; схема `symbols` допускает новый `kind` без переделки |

Следствие для модели данных: пункт 4.2 из `LocRecord` вырастает в
`SymbolRecord(kind, name, place, region)`; `kind` конечен и сериализуем, «место» остаётся
двухвариантным (файл | `Buffer.id()`), но вариант буфера не персистится.
