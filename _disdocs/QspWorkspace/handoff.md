# Handoff: `QspWorkspace` — идентичность проекта, кэш, живой индекс

Назначение файла — **перенос состояния между чат-сессиями**. Здесь нет обоснований: решения и их
причины живут в [`cache_architecture.md`](./cache_architecture.md) (Р- и Д-номера), задачи — в
[`refactor_plan.md`](./refactor_plan.md). Этот файл отвечает только на вопросы «где мы», «что мешает»
и «какой следующий шаг».

## 0. Как быстро восстановить контекст в новом чате

1. Приложить к первой реплике `cache_architecture.md` + `refactor_plan.md` — этого хватает, чтобы
   контекст собрался за один шаг.
2. Проверить окружение: `git rev-parse --abbrev-ref HEAD` (должно быть `ws_ref`) и
   `git status --short`.
3. Полезные записи памяти (подтягиваются автоматически, но на всякий случай по названиям):
   «QSP WS: идентичность проекта — folders[0] не равен папке проекта», «QSP workspace cache:
   хранение в cache_path и идентичность по .sublime-project», «Решение: QspWorkspace = живой индекс
   локаций (этап 1), файл кэша вторичен», «Remove QSP_WORKSPACES entry on project close»,
   «Overwrite empty QspWorkspace cache file», «Sublime Text: закрытие окна/выход — какие хуки
   реально приходят».

Инварианты И1–И4 (проверяются тестами): И1 — вне папок окна не индексируем, безымянные буферы с
qsps-подсветкой индексируем в RAM; И2 — виртуальный WS есть у любого окна с ≥1 папкой, файл только
при `.sublime-project`; И3 — индекс обновляется по изменению текста, а не только load/save; И4 —
расхождение с диском по `mtime/size/md5` → перескан, несохранённый буфер всегда выигрывает и наружу
не сериализуется.

## 3. Фактическая база (что уже измерено, чтобы не перепроверять)

Снимки — [`window.extract_variables().jsonc`](./window.extract_variables().jsonc) (9 шт.), логи —
два прогона датчика. Полный разбор: §2, §2.1, §2.2 архитектурного документа.

- **Д1**: `extract_variables()['folder']` **всегда** равен `folders()[0]` (включая пустое окно и
  активный файл вне папок). Идея «возить ключ по `${folder}`» похоронена.
- **Д2/Д7**: `folders[0]` ≠ папка проекта (у JAD первой стоит `[lib]\easy.math.3`); ST-проект ≠
  QSP-проект (`qsp-project.json`).
- **Д8/Д9/Д10/Д11**: внутри `on_pre_close_project` `folders()` и `project_file_name()` ещё
  заполнены, **но** `folders()` уже мог сузиться; записи закрытых проектов из `QSP_WORKSPACES` не
  удаляются; `window.id()` переживает смену проекта в том же окне → accessor сверяет `identity`.
- **Д15/Д16/Д17**: закрытие окна с проектом даёт `on_pre_close_project`; хука `on_close_window`
  в API **нет** (правильно `on_pre_close_window`, 4050); `on_pre_close(view)` приходит после
  закрытия проекта и с `view.window() == None`; **на выходе из ST не приходит ни одного события**.
- **Д18/Д19**: окно «Open Folder» не породило записи в реестре (под вопросом И2); `win_id`
  нумеруется заново каждый запуск → RAM-ключ не персистим.
- **Д6**: кэш не прунится — в живом `qsp-project-workspace.json` мёртвые пути `[examples]\…`.

## 4. Открытое — то, что блокирует код

1. **СНЯТО (третий прогон датчика, rev 3; арх. документ §2.3, Д20–Д26):** все четыре измерения
   закрыты — **Э7** (`on_exit` доходит, пишет файл, но API в нём мёртв; прямой выход не даёт
   per-window хуков → prepared payload+path), **Э9** (`on_pre_close_project` раньше
   `on_pre_close_window`; безпроектное окно — только window), **Э8** (RAM-WS безпроектного окна
   строится лениво по первому `.qsps`), **Э5-подтверждение** (`plugin_unloaded` приходит при выгрузке
   пакета, но не на выход).
2. **СНЯТО — Flush на выходе из ST:** `on_exit()` доходит и пишет файл чистым Python-IO (Д20/Д21);
   вариант (1) «смириться и пересобирать по mtime» больше **не** нужен как единственный — R5 принят
   с точками `on_pre_close_project` (основная) + `on_exit` (резерв, по подготовленным payload+path);
   таймер-автосейв (вариант 3) не вводим. Можно писать `save/load` (§6).
3. **Дебаунс `on_modified_async`** — задержка и очередь «грязных» вью не назначены: назначаем по
   замерам, а не на глаз (объём — перескан одного вью уже реализованным `refresh_qsplocs`).
4. **Мелочи к подтверждению**: имена файлов кэша и `index.json` (R3); состав полей схемы v2 (R4).

## 5. Как поднять датчик (прогоны Э7–Э9) — **ВЫПОЛНЕНО, 06.11; датчик снимается**

> Все четыре сценария ниже отработаны (лог rev 3 от 06.11, разбор — арх. документ §2.3).
> Блок датчика больше не нужен: удаляется целиком после первого коммита по идентичности (§6).

1. Плагин в ST работает **копией**, а не из репозитория: `%APPDATA%\Sublime Text\Packages\QSP`
   (папка, не `.sublime-package`). Перенести туда `QSP.py` (и `typings/` не нужен — он только для
   pyright) и сверить: `(Get-FileHash a).Hash -eq (Get-FileHash b).Hash`.
2. Ревизия датчика в строках лога — поле `rev` (сейчас `3`); выключатель `QSP_PROBE`.
3. Сценарии: закрыть окно с проектом → File → Exit → заново запустить → открыть окно без проекта
   (Open Folder) и `.qsps`-файл в нём → переименовать пакет `QSP` → `QSP.off` и обратно (тест
   `plugin_unloaded`, безопаснее удаления).
4. Лог: `sublime.cache_path()` = `%LOCALAPPDATA%\Sublime Text\Cache\QSP\identity-probe.log`
   (обратите внимание: `Cache` и `Packages` — в разных деревьях, `Roaming`).
5. После принятия R5 удалить весь блок датчика (`# ВРЕМЕННО` … `plugin_unloaded`) одним движением.

## 6. Следующий шаг, конкретно

Первый коммит (шаг 2 списка в `refactor_plan.md`):
`qwen fix(ws): workspace identity + empty-window guards; drop out-of-folder indexing` — пункты
**2.1, 2.2, 2.7, 2.9**. Что в него входит:

- в реестре — хелпер `identity_of(window)` (диск) и accessor по `window.id()` **без создания**
  записи + `pop` при закрытии (сейчас `_get_qsp_ws` создаёт запись на demand — корень фантомов);
- `on_pre_close_project`: не читать `extract_variables()`, не сохранять при пустом `identity`
  (окно без `.sublime-project`), писать по своему `identity` вместо аргумента-пути;
- `on_associate_buffer_async` и `QspProject._work_dir_init`: guard на пустой список папок;
- `on_post_save_async`: проверка `is_path_in_project_folders` (И1);
- после чего маркер 2.5 (`close_project`/`project_is_closing`) становится лишним — удалить.

Дальше по списку коммитов: реестр (4.1, 4.4) → модель записи (4.2, 4.3) → живой индекс локаций
(2.8, R5) → дубликаты/сканер (4.6, 4.5, 2.3, 2.4) → константы и лог (4.8, 4.9) → кэш v2 +
инкрементальный скан (4.7, R3, R4) отдельным объёмным коммитом.
