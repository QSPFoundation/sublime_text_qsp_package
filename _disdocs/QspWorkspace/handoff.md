причины живут в [`cache_architecture.md`](./cache_architecture.md) (Р- и Д-номера), задачи — в
[`refactor_plan.md`](./refactor_plan.md). Этот файл отвечает только на вопросы «где мы», «что мешает»
и «какой следующий шаг».

## 2. Каркас решений (детали и причины — по ссылкам)

| # | О чём | Статус |

Инварианты И1–И4 (проверяются тестами): И1 — вне папок окна не индексируем, безымянные буферы с qsps-подсветкой индексируем в RAM; И2 — виртуальный WS есть у любого окна с ≥1 папкой, файл только при `.sublime-project`; И3 — индекс обновляется по изменению текста, а не только load/save; И4 —
расхождение с диском по `mtime/size/md5` → перескан, несохранённый буфер всегда выигрывает и наружу
не сериализуется.

## 3. Фактическая база (что уже измерено, чтобы не перепроверять)

Снимки — [`window.extract_variables().jsonc`](./window.extract_variables().jsonc) (9 шт.), логи —
два прогона датчика. Полный разбор: §2, §2.1, §2.2 архитектурного документа.

- **Д1**: `extract_variables()['folder']` **всегда** равен `folders()[0]` (включая пустое окно и
  активный файл вне папок). Идея «возить ключ по `${folder}`» похоронена.
- **Д2/Д7**: `folders[0]` ≠ папка проекта (у JAD первой стоит `[lib]\easy.math.3`); ST-проект ≠
  QSP-проект (`qsp-project.json`).
- **Д8/Д9/Д10/Д11**: внутри `on_pre_close_project` `folders()` и `project_file_name()` ещё
  заполнены, **но** `folders()` уже мог сузиться; записи закрытых проектов из `QSP_WORKSPACES` не
  удаляются; `window.id()` переживает смену проекта в том же окне → accessor сверяет `identity`.
- **Д15/Д16/Д17**: закрытие окна с проектом даёт `on_pre_close_project`; хука `on_close_window`
  в API **нет** (правильно `on_pre_close_window`, 4050); `on_pre_close(view)` приходит после
  закрытия проекта и с `view.window() == None`; **на выходе из ST не приходит ни одного события**.
- **Д18/Д19** (уточнено третьим прогоном, Д25): окно «Open Folder» (`project_file: null`) получает
  RAM-WS **лениво, при первом индексировании `.qsps`**; `win_id` нумеруется заново каждый запуск →
  RAM-ключ не персистим.
- **Д6**: кэш не прунится — в живом `qsp-project-workspace.json` мёртвые пути `[examples]\…`.
- **Д27** (приёмка 2.8, 09.11): `is_path_in_project_folders` до фикса возвращала `True` для любого
  файла того же диска (непустой `commonpath` ≠ вложенность) → И1 не работала нигде; исправлено
  сравнением `commonpath == папка` (план 2.10, `function.py`).

## 4. Открытое — то, что блокирует код

1. **СНЯТО (третий прогон датчика, rev 3; арх. документ §2.3, Д20–Д26):** все четыре измерения
   закрыты — **Э7** (`on_exit` доходит, пишет файл, но API в нём мёртв; прямой выход не даёт
   per-window хуков → prepared payload+path), **Э9** (`on_pre_close_project` раньше
   `on_pre_close_window`; безпроектное окно — только window), **Э8** (RAM-WS безпроектного окна
   строится лениво по первому `.qsps`), **Э5-подтверждение** (`plugin_unloaded` приходит при выгрузке
   пакета, но не на выход).
2. **СНЯТО — Flush на выходе из ST (реализовано, коммит 9):** `on_pre_close_project` пишет v2 в
   `cache_path` (атомарно, по подготовленному `_cache_path`); `on_exit()` (4050) флашит все живые WS
   чистым Python-IO без sublime-API (Д20–Д22). Таймер-автосейв не вводим.
3. **Дебаунс `on_modified_async` — механизм реализован (коммит 6), задержка ждёт замера.**
   Механизм: per-view счётчик поколений (`QspWorkspaceHandlers._locs_gen`), каждая правка планирует
   свой таймер через `sublime.set_timeout_async`, устаревшие гасятся в колбэке; словарь чистится
   последним колбэком вью. `_LOCS_DEBOUNCE_MS = 250` — **кандидат**: на приёмке проверить, что при
   непрерывном наборе completion не блокируется, а после паузы индекс обновлён; при необходимости
   подобрать значение замером и поправить константу.
4. **Мелочи к подтверждению**: имена файлов кэша и `index.json` (R3); состав полей схемы v2 (R4).

## 5. Как поднимался датчик (прогоны Э7–Э9) — **ВЫПОЛНЕНО, датчик удалён из кода**

> Все четыре сценария отработаны (лог rev 3 от 06.11, разбор — арх. документ §2.3). Блок датчика
> удалён из `QSP.py` (`# ВРЕМЕННО` … `plugin_unloaded` + осиротевший `import time`); шаги ниже —
> историческая справка, как это поднималось.

1. Плагин в ST работает **копией**, а не из репозитория: `%APPDATA%\Sublime Text\Packages\QSP`
   (папка, не `.sublime-package`). Перенести туда `QSP.py` (и `typings/` не нужен — он только для
   pyright) и сверить: `(Get-FileHash a).Hash -eq (Get-FileHash b).Hash`.
2. Ревизия датчика в строках лога — поле `rev` (сейчас `3`); выключатель `QSP_PROBE`.
3. Сценарии: закрыть окно с проектом → File → Exit → заново запустить → открыть окно без проекта
   (Open Folder) и `.qsps`-файл в нём → переименовать пакет `QSP` → `QSP.off` и обратно (тест
   `plugin_unloaded`, безопаснее удаления).
4. Лог: `sublime.cache_path()` = `%LOCALAPPDATA%\Sublime Text\Cache\QSP\identity-probe.log`
   (обратите внимание: `Cache` и `Packages` — в разных деревьях, `Roaming`).
5. После принятия R5 удалить весь блок датчика (`# ВРЕМЕННО` … `plugin_unloaded`) одним движением.
